**一个已知局限**：多轮那 15 道**全部**埋了错误前提，没有对照题。所以一个「逢人就质疑上一轮」的模型能在这套题上拿满分——无法把「正确地坚持」和「无差别地质疑」分开。单轮那组有 10 道基线题做这个对照，多轮这组没补。要扩题集的话，这是第一个该补的。

## 为什么留着那两个 DEPRECATED 文件

`grade-regex-DEPRECATED.py` 是最早用正则自动判分的脚本。它报出来的弃答率是 **18–26%**。

我抽查了 6 条被它判为「直接作答」的响应——**6 条全都是明确纠正了错误前提的**。真实值是 94–98%。

也就是说，那个脚本把结论整个搞反了。如果不抽查，文章会写出一个完全错误的判断。

**所以这两个文件不是垃圾，是证据。** 测量工具的失败和被测对象的失败长得一模一样：一个 0% 可能是模型不行，也可能是你的 key 过期了。不去核对，两者看起来完全一样。

文章第八节讲的就是这件事。

## 这套方法不绑定 FUMO

`reproduce.py` 改三行就能测别的模型：

```python
ENDPOINTS = {
    "你要测的模型": ("API 地址", "模型名", "环境变量名"),
}
```

判分标准（`RUBRIC`）与原文完全一致。Gemini、Kimi、DeepSeek、本地模型都可以。

跑法：

```bash
$env:ZENMUX_API_KEY="你的key"
python reproduce.py
```

## 已知的限制，一次列全

1. **多轮组没有对照题**（见上）。
2. **单轮错误前提题饱和**：四个模型识别率 97–100%，题出得太简单，这组基本没有区分度。
3. **测量噪声约 ±11 个百分点**：同一模型、同一批题、同一套判分标准，隔半个月重跑差了 11 个点（fusion-max 69% → 58%）。**本文所有百分比，差距小于 11 个点的都不要当结论看。**
4. **网络链路不对等**：FUMO 为直连，两个对照经 ZenMux 网关，延迟绝对值不完全可比，所以文章看的是增量而非绝对值。
5. **参数不完全一致**：Opus 5 不支持 `temperature`，为避免只给一个模型开特例，四方统一「不指定温度」，各用各的默认值。
6. **判分用 LLM**：判分结果经人工抽样校验，但裁判模型本身也可能出错。原始响应全部公开，欢迎自己判一遍。
